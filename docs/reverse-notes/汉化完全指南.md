### 0.4 第 1-12 节要点（原文丢失，据现有资料补记）

- **FFCS v2 WAD**：`FFCS` 头 256 B，chunk 行 `INDX/DATA/CSUM/ASET/PTHS`；块数据是 sges 压缩，解压后常为 `UCFX` 容器（`UCFX` + 头 + 20 B/chunk 描述 + 数据区，尾部 `CSUM` = JAMCRC）。
- **stringdb**：UCFX 内 `INFO/KEYS/STRS` 三段；KEYS = `(u32 hash, u32 byte_offset)`，STRS = UTF-16LE 堆；`build_stringdb` 保留原堆、追加新文本并重指向，未改条目字节级不变。
- **键哈希** = Pandemic `pandemic_hash_m2`：键名去方括号、大小写不敏感。
- **GFx 字体块**：两种形态——
  - `0x99E77ACE` 的 `UCFX(INFO/CHAR/MTRL)`（语言字体 `english_20`/`english_18`，271 字符 × 14 B）；
  - `0x99E77ACE` 的 `CFX`（zlib 压缩的 GFX 字体记录，`fonts_enext`，payload 16,384 B）；
  - `0xFE0E8320` = FontTextureInfo（shell 的 `_normal_font` 等）。
- **图集**：`0xF011157A`，UCFX `NAME/INFO/BODY`，DXT5；**alpha 才是字形掩码**，RGB 全 255。
- 替代资料：`.workbuddy\work\docs\format_reference.md`（52 KB）、`field_guide.md`（44 KB）、`asset_injection_playbook.md`（26 KB）、`font16_format.md`（5 KB）。

### 14.2 `FUN_004bfe20` — 语言 WAD 挂载

```c

```

确认 v1.0：索引 `0x01176018`、名字表 `0x00CF281C`、函数 `0x004BFE20`。

### 14.3 `FUN_004ac8e0` — 语言块字体加载

- 识别 `MTRL`(0x4c52544d) / `INFO`(0x4f464e49) / `CHAR`(0x52414843)；
- **MTRL 每材质 400 字节**（0x190），数组 `page_count * 400`；
- **CHAR = 码位表 + 12 字节/字形记录**（`count * 0xc`）；
- 与自建 `build_langfont` 结构一致。

### 坑 14.1 CHAR 是 12 字节/字形，不是 14

- 现象：按 `vz-patch` 的 `57,876 B / 4,134 = 14 字节` 去算原始 `fonts_enext`/`english_20` 的字符记录，全部错位。
- 原因：`FUN_004ac8e0` 读的是 **12 字节/字形记录**（`count * 0xc`）；`vz-patch` 里的 14 字节是**重建后**的"字符记录 + 附加字段"，两套不是同一个东西。
- 修复：解析**原始**块按 `count*0xc`；只在解析自己重建的块时才用 14 字节口径。

### 14.4 `FUN_006226d0` / `FUN_00623c90` — 文本宽/布局

文本指针 `+0x130`（UTF-16）；`0x5D`(']') 与 `0x4F`('O') 有特殊分支；字形 lookup `FUN_004ace60`。
**布局与宽度和字体无关**——字体图集问题不在这里。

### 坑 14.2 把"码位链路理解错"误判成"引擎 UV 不一致"

- 现象：单槽位（`0xC0`）画汉字不生效，游戏仍显示 `À`。
- 错判：当时结论写成"图集 UV 映射/页解析与游戏实际不一致"，于是跑去改引擎。
- 真正原因：**码位链路搞错了**——码位表下标是 `glyphIndex`，不是码位值本身；要经 `pairs[glyphIndex]` 再查 UV。
- 修复：第 15 节按正确链路重做，一次通过（`U+00C0` → uv#117 → "按"）。
- **教训**：先怀疑自己的解析，再怀疑引擎。

## 15. english 字体链路打通（里程碑，2026-11-08 深夜）

**目标**：让 english 模式标题显示中文。

### 坑 15.1 `pages=2` 是把 `width=512` 的字节读成页数

- 现象：以为 `fonts_enext` 有多页，按页去算 UV，怎么都对不上。
- 原因：`parse_texture_chunk` 里 `pages` 字段实际读到的是 `00 02`（512 的高字节），**`fonts_enext` 只有一页 512×256**。
- 修复：UV 记录 24 字节 = 4×f32 `Left/Top/Right/Bottom` + 2×f32 origin；像素矩形 = `(Left*512, Top*256)-(Right*512, Bottom*256)`。

### 坑 15.2 码位表下标 ≠ 码位

- 现象：按码位值直接索引 UV，位置全错。
- 原因：正确链路是 **`码位表下标 = glyphIndex` → `pairs[glyphIndex] = uvIndex` → `UV[uvIndex]`**；`pairs` 表在 UV 表之后：`u16 nFonts + u16 fontId + u16 count + count×4`。
- 修复：按 glyphIndex 走两跳，不要直接拿码位查 UV。

### 坑 15.3 图集 RGB 全 255，掩码在 alpha

- 现象：导出图集看是纯白，以为图集空。
- 原因：DXT5 的 RGB 全 255，**字形在 alpha**（每 16 字节块的前 8 字节）。
- 修复：解码/编码都只处理 alpha 8 字节。

### 坑 15.4 文本写真汉字会回退成 `À`

- 现象：stringdb 里写"按"，游戏显示 `À`。
- 原因：字体码位表里没有 CJK 码位。
- 修复：用**捐赠码位**——图集里已有、且游戏文本用不到的拉丁扩展码位（如 `U+00C0`）。

### 验证成功

- `U+00C0` 槽（glyphIndex 126 → uvIndex 117 → rect `(254,0)-(277,32)`）画"按"；
- 标题 key `0x5085D0F3`（`Press %s to continue.`）→ `chr(0x00C0) + "%s"`；
- 部署 `loading-patch.en2.wad` + `shell-patch.en2.wad`，标题显示 **"按Space"** ✅

> 注：Ghidra 报告样例把 U+00C0 标成 127/118（其实是 U+00C1），自解析得 126/117，实测正确。

### 坑 20.2 无法运行时验证，导致盲试

### 当时列的排查方向（第 24 节给出了答案）

1. 逐字段 diff 原始 vs 扩展版，找不变量；

## 25. 界面乱码的真根因：patch 按 asset hash 覆盖

### 现象

部署 66 槽码位版后，OPTIONS 页右侧出现 **"这有容内 / 容内 / 垢 / 妨 / 们退 / 开戏"**，底部出现 **"火得上内容"**。

### 坑 25.1 误判 UV 字段顺序

- 现象：怀疑 `(q0,q1,q2,q3)` 不是 `(left,top,right,bottom)`。
- 验证：用 UV 从图集裁 `A`（uv#32）→ 得到完整清晰的 `A`。
- 结论：UV 语义**正确**，单位是图集宽高比例。排除。

### 坑 25.2 误判 origin 对齐

- 现象：以为所有字体都能用 UV 第 5/6 个 float 当字形原点。
- 验证：`_shell_normal_font` 的 `A` 的 `(q4,q5)=(0.2715,0.5703)` 恰好在槽内，但 `00C0` 的槽是 `px(126,0)-(150,33)`、origin 给 `(139,146)`，**完全在槽外**。
- 结论：`_shell_*` 不能用 origin 对齐，必须在 UV 矩形内部排版（`fonts_enext` 相反，见 26.3）。

### 坑 25.3 真根因：patch 按 asset hash 覆盖

`ffcs_patch_wad.py` 的规则是 **"matching hashes override originals"** —— 覆盖判据是 **asset hash**，不是块路径。

| patch | 块 | 内容 |
|---|---|---|
| `vz-patch.wad` | `blocks\VZ\english_P000_Q3.block` | 3×字体块(58,820 B) + stringdb + 2×图集(**2048×2048**) |
| `shell-patch.wad` | `blocks\Shell\english_P000_Q3.block` | 4,738 B 字体块 + stringdb + 2×图集(**256×512**) |

共享 hash：

```
40BA4038 / 6C3B162F   ← 语言字体图集（vz 给 2048，shell 给 256×512）
13C26ABC / 093F42E5   ← 语言字体记录（vz 给 58,820 B 含 CJK，shell 给 4,738 B 仅拉丁）
```

**vz-patch 的这三对资源按 hash 覆盖了 shell.wad 的同名资源**，所以 shell 实际用的是 vz 的 CJK 字体 + 2048 图集，而 66 槽码位是为 512×256 拉丁图集设计的 → 码位被解释成 2048 图集上的其它汉字 → 乱码。

"退""开""戏"偶尔对得上，是因为两套汉字表有部分重合。

### 坑 25.4 修了 hash 冲突，但字体选错（方案被推翻）

- 做法：`build_ui_zh3.py` 直接把 48 条写成**真汉字**（赌 vz-patch 的 CJK 字体记录 + 2048 图集会生效），产物 `shell-patch.ui_zh3.wad`（3,866,624 B，`5C13990F`）。
- 结果：**实测仍是方块**。
- 原因：shell 界面根本不用那套 CJK 语言字体，用的是 `fonts_enext`（见第 26 节）。
- 教训：hash 覆盖只是"为什么乱码"的解释，不能推出"该用哪套字体"——字体归属必须单独证明。

## 28. 全透明图集探针：字体归属定案

### 坑 28.1 涂黑单个字卡在 CHAR 结构

- 现象：想涂黑 `english_20` 的 `A`，按 entry 解析时 `body[:4]` 不是 `CFX\x08`，解码失败。
- 原因：`0x99E77ACE` 有两种形态——`fonts_enext` 是 CFX，`english_20/18` 是 **UCFX(INFO/CHAR/MTRL)**：

```

CHAR  n×14 B 字符记录
MTRL  840 B  材质
```

- 尝试：单 entry 重组块 → `decode failed: ''`（UCFX 头结构不能简单拼）。

### 换方法：整张图集置透明

不依赖 UV 解析。把 `vz-patch` 两张 2048 图集的 alpha 全部置 0，判读极简单：

- 图集被采样 → 用它渲染的文字**变空白**
- 图集没被采样 → 屏幕**毫无变化**

产物 `work/probe_blackout/vz-patch.clearatlas.wad`（3,342,336 B，`958C6BEE`）。

### 结果（实机）

| 观察对象 | 现象 | 结论 |
|---|---|---|
| 对话字幕、弹药数、任务提示 | **全部空白** | 走 `english_20`/`english_18`，且 **2048 图集被引擎正常采样** |
| PDA（MAP/STOCKPILE/INFO 页） | **依旧方块** | PDA 主文本**不走** `english_20` |

**这推翻了此前"PDA 用 english_20"的判断。**

### 坑 28.2 以为 `vz-patch` 改坏了 english_20 的格式

- 现象：一度怀疑 58,820 B 的字体块格式错误。
- 验证：原始 `shell.wad` 的 english_20 **本来就是 UCFX(INFO/CHAR/MTRL)**（4,738 B = INFO 16 + CHAR 3,794 + MTRL 840，271 字符 × 14 B）。

## 30. B 路线设计稿：fonts_enext 扩容（2026-11-10）

### 30.1 两条关键发现

**发现 1：CJK 码位天然升序，不需要重排 glyph。**

现有码位最大 `0x2183`，CJK 从 `0x4E00` 起 —— 追加后天然满足 `find_fonts` 的升序校验，**glyphIdx 全部不变**，因此 kerning 的 `(a,b)` 索引仍然有效。这条避免了"重排 glyph → kerning 失效 → 拉丁字距错乱"的连锁问题。

**发现 2：`tail` 可以原样平移。**

`0x7D62C0` 反编译显示不读尾段（导出器元数据），扩数组时 tail 只需整体后移，内容不必重算。

### 30.3 扩容实施步骤（原稿 30.4，可直接执行）

1. **字表**：`work\translate\zh_full.tsv` 的 CJK 用字（实测 **2,258** 个）∪ GB2312 一级（3,755）→ 约 **3,800 字**。
2. **码位表**：原 486 个 u16 保留，尾部追加 N 个 CJK 码位（N = 字表规模），天然升序。
3. **`glyph_count`**：486 → 486 + N。
4. **advance / res**：原值保留，各追加 N 个 u16（advance 取固定值，如 960 = 48px@20x；res 取 0）。
5. **`uvCount`**：199 → 199 + N。
6. **UV 数组**：
   - 前 199 项：各坐标 × `(512/2048, 256/2048)` = **×0.25**（原字形落到 2048 图集左上 512×256 区域）
   - 新增 N 项：按 2048 网格独立计算（32×32 格 → 64 列 × 56 行 = 3,584 格；**格子必须从第 8 行起**，见下条）
7. **pairs**：
   - 前 199 项原样（`uvIdx` 不变，因为 UV 前 199 项顺序不变）
   - 新增 N 项：`(glyphIdx = 486+i, uvIdx = 199+i)`
8. **tail**：整体后移到新 `pairs_end` 之后，内容原样。
9. **图集**：512×256 → **2048×2048**，BODY = 4,194,304 B；**原图必须原样保留在左上 512×256**，新汉字只能从 **第 8 行（y=256）** 起画——原稿漏了这条，31.4 踩坑后补上（否则汉字覆盖拉丁字母区，一个字母显示成几个汉字）。

1. **绝不用 `G.rebuild(f)` 重建整个字体记录，绝不改原有 advance**（22.1：曾导致"全部文字叠在一起"）。
2. **图集必须是真正的 2048×2048**（INFO 写 2048，BODY 4,194,304 B），不能只改 INFO。
3. **原图区（左上 512×256）必须保留，新字从第 8 行起**（31.4）——31 节补上的关键一条。
4. 新 CJK 的 UV 必须按 **2048 网格**独立算，不能用 512×256 坐标反推（`build_final_vzpatch.py` 疑似在此出错）。

6. 自检门槛：用 3 个原 ASCII 码位（`A`/`g`/`0`）的 UV 裁图，**必须仍是原字母**（证明旧 UV 缩放正确）。

## 35. 2026-11-12 晚：ASET 根因与 2048 图集加载验证

### 35.1 根因：patch 的 ASET 字段写错（决定性的）

- 原始 WAD 的 ASET 条目是 `(asset_hash, u1=0xFFFFFFFF, u2=0x00XXFFFF, u3=小整数)`；
- E/F/H 的构建器写成了 `(hash, u1=0xFFFFFFFF, u2=0, u3=type_hash)`；
- **引擎按 `(hash, u3)` 匹配**，u3/u2 不符 → **整个 patch 块被忽略，游戏继续读原版**；
- 这解释了此前所有"sha256 变了、画面没变"的现象（F/H 版从未真正加载过）；
- 修正：从原始 WAD 的 ASET 表按 hash 复制 `u1/u2/u3`，只重写 `u2` 高 16 位（新块索引）。

### 35.2 崩溃：ASET 修好后第一次真正加载

- ASET 修正后，引擎第一次真正加载 `2048² 图集 ×10 + resident 43.8 MB` → **C0000005 闪退**；
- 26 节版 resident 仅 3.2 MB、图集 512×256 → 正常；
- 结论：**崩溃不是 ASET 格式问题，是体积**（10 张 2048 图集塞进 resident）。

### 35.3 验证：min1 正常

- `shell-patch.min1.wad`（只 `_bold_font` entry 0 + 图集 #27，4,620,288 B，resident 7.3 MB）→ **游戏正常启动**；
- 证明单张 2048 图集可以加载，43.8 MB（10 张）才会撑崩；
- 减量方向确定：**只做界面实际用的少数字体**（日志出现 3 个：1×512×256 + 2×512×128）。

## 37. 2026-11-12 深夜：GFx 字体函数地址校正与踩坑记录

### 37.1 三区域运行时 dump（修正 RVA/VA 后）

`m2_dump_region` 之前把 RVA 当 VA（`g_base` 赋值顺序错），读到全 0；修正后：

```
0x7D45A0: 57 8B F9 E8 88 FF FF FF ... C2 04 00   ← 另一个函数的尾部（ret 4）
0x7D45C3: CC ...
0x7D45D0: 8B 46 04 33 C9 3D 89 1E 47 56 ...      ← GFxFont 构造入口（无 55 8B EC！）
0x7D68D8: E8 F3 DC FF FF                          ← call 0x7D45D0（目标吻合）
0x7FC120: 55 8B EC 83 E4 C0 83 EC 74 ...          ← 有效函数（标准序言）
```

**结论**：

- `0x7D45D0` **确实是函数入口**，但它是**无帧指针**的 `__thiscall`（直接 `mov eax,[esi+4]`），不是 `55 8B EC`——所以"扫描 55 8B EC"会误判它不是入口；
- `0x7D68D8` 确实是 `E8` call `0x7D45D0`，**Ghidra 没误判**；
- `0x7FC120` 是**有效函数**（GLIB），但**一次都没被调用**（无 hit）→ 菜单字体不走它。

### 37.2 为什么 CTOR hook 会把 ecx 变成 0x246

- `0x7D45D0` 无帧指针，MinHook 覆盖 5 字节会截断指令（`8B 46 04 33 C9` = 5 字节，刚好边界）；
- 更关键：**hook 入口后，CALL68（0x7D68D8）调用它时走 detour，detour 的 pushal/寄存器保存链破坏了调用者设置的 ecx**（0x7D45D0 的 ecx 是调用者传的 `this`，被 detour 改成了 0x246）；
- 结论：**不要在 0x7D45D0 入口 hook**；要拿字体对象，用 **0x7D68D8 的 call 前 ecx**（但探针读取位置也要对，见 37.3）。

### 37.3 CALL68 探针的 ret=1 问题

- `CALL68 esp0=... ret=00000001`：stub 传的入口 esp 读取位置不对（ret 应为返回地址，不是 1）；
- 栈参数 arg1/2/3 按 GFxFont 布局读全是垃圾 → **0x7D68D8 的调用参数不是字体对象**（this 由 call 前 ecx 传，不在栈）。

### 37.4 关键踩坑清单（本轮）

| 坑 | 现象 | 修正 |
|---|---|---|
| dump 用 RVA 当 VA | 全 0 / unreadable | `g_base + RVA`，且 `g_base` 赋值后再 dump |
| `0x7D45D0` 无 `55 8B EC` | 误判"不是入口" | 它仍是入口，只是无帧指针 |
| hook `0x7D45D0` | 破坏调用者 ecx（0x246） | 不 hook 入口，用 call 点/返回点 |
| CALL68 栈参数 | 全垃圾、ret=1 | this 在 call 前 ecx，不在栈 |
| `0x7FC120` 无 hit | 菜单字体不走它 | 需另找字体库入口 |

### 37.5 下一步

1. 在 **0x7D68D8 的 detour 里保存 call 前的 ecx**（push ecx / 读 [esp] 前的 ecx），确认它是不是字体对象；
2. 若是 → 在 call 返回后 inject_font；
3. 若 `0x7FC120` 真没被调用 → 菜单字体（entry#17）的创建在别的函数，需从 `0x8031C0` 的调用者（0x802453）往下追。

## 43. 字体资产与排版（工程精华）

> 以下为主线程与外部分支多轮实机验证后的经验，直接决定"字能不能显示/排版对不对"。

### 43.1 游戏有 4 套独立字体

| # | 字体名 | 位置 | 格式 | 用途 |
|---|---|---|---|---|
| 1 | Gunplay（fonts_enext） | Loading.wad 块1/5 | GFx CFX/SWF | shell 界面：主菜单、加载、退出确认框 |
| 2 | Franklin Gothic Medium（fonts_ru） | Loading.wad 块2/7 | GFx CFX/SWF | 俄语本地化（英文版不用） |
| 3 | shell 字体（_shell_*_font） | shell.wad 块6/7/27/28 | GFx CFX/SWF | 菜单细节 |
| 4 | font_16_main | vz.wad 块3079（256×256 DXT5 FTGA） | FTGA 位图字体 | 游戏内 HUD/字幕 |

**判断"某段文字用哪套字体"唯一可靠方法 = 实测**（造"把某字体字母 e 涂黑"的补丁，进游戏看哪些 e 变黑），不要靠推测。

### 43.2 引擎一致性校验（最大坑）

- 引擎校验 **原生度量段 ↔ GFx 尾段** 的一致性；
- **任何原生段改动**（哪怕只改 2 字节 advance），只要尾段没同步 → **整份字体资产回退到原版** → 中文乱码/空白；
- **回退 ≠ 崩溃**：文字照常渲染，但用原版字体+图集；
- **只改图集位图（回收法）永远安全**；改 advance/追加字形必须同步尾段。

### 43.3 "追加码位扩容"三次实验全部失败

- 引擎在**加载时固化字形表**（追加字形 → 查找失败/回退）→ **容量上限 27~42 字**（只剩槽位可用）；
- 结论：**扩字体的静态路子走不通**，只能"回收槽位"或"运行时注入"。

### 43.4 排版硬约束（比字体校验更隐蔽的坑）

- 菜单 SWF **按英文原文排版**（文本框宽度/锚点/居中按英文长度算）→ 译文更长 → **溢出裁剪**（只剩末尾 1~2 字）；
- **advance 不随图集变**（槽位字宽仍是拉丁窄宽）→ 汉字超宽 → **相邻重叠**；
- **核心教训**：**图集能画出汉字 ≠ 引擎能正确排版**；
- 只翻"与英文长度相当或更短"的词、且 advance 装得下汉字宽度，才可能过关；
- **验证纪律**：任何字体/文本改动必须**逐屏实机验证**（主菜单/暂停/设置各页/载入/HUD），不能只测一个画面就推广。

### 43.5 字体容器格式（0x99E77ACE，实测）

```
INFO 16B : u32=7, u32=30, u32=0x00240027, u32=字形数
CHAR     : 字形数 × u16 码位 + 字形数 × 12B 度量
  度量 12B: +0 x0f  +2 x1f  +4 y0f  +6 y1f  +8 advance(twips)  +10 h
  像素坐标：x = x0f/256, y = y0f/128   ← 两者分母不同（关键坑）
MTRL 840B: 材质（本轮未用）
```
验证：按上式把矩形画回贴图与墨迹做 IoU（191/271 命中）。

### 43.6 可牺牲槽位（汉字用）

- 英文正文只用 ASCII（95 个），Latin-1 重音字母实际用不到；
- **可牺牲码位 96 个**（非 ASCII、非引擎符号区、英文原文未出现），其中 size≥16 的 42 个；
- **最大槽位 U+00C0(À) box20=20×28 adv=21.6** → 可放 20px 汉字；
- 槽位 advance **固定**（不能改）→ 汉字间距 = 原拉丁 advance（排版偏紧）。

### 43.7 贴图通道（DXT5）

- **RGB = 白色字面**（黑底白字，运行时染色）；
- **alpha = 黑色描边**（字面外扩 1~2px 的实心轮廓）；
- 重画汉字必须**两处都写**（RGB 字形灰度 + alpha 膨胀 1px），才能得到一致的"白字+黑描边"。

### 43.8 资产分布与 ASET

- 电影资产：shell.wad blk18 scaleform_shell（1.16MB ActionScript）、blk9 japanese_P000_Q3（日文 shell 电影包 671,744B）；
- 字体包：cfx_pack（ASET u3=0x17）；
- **ASET u3 = type_id**：0x17 字体/电影包、0x1B 贴图、0x23 Lua 脚本；
- 哈希函数未破解 → 靠 UCFX NAME 段 + ASET 反查定位资产。

### 43.9 运行时注入（绕过引擎校验）

- 静态改 wad 会被引擎一致性校验卡死（回退）；
- **运行时在 reader（0x7D62C0）注入**（改字体对象 glyphTable/tex）→ **绕过校验**（不碰 wad 结构）；
- 这是本项目"游戏内 HUD/字幕中文"成功的关键（fonts_enext 2048 + 3,584 CJK）。
